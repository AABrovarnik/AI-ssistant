# Концепция расширения AI Secretary

Статус: draft для согласования направления

## 1. Новая роль ассистента

AI Secretary должен стать не только менеджером задач, а персональным слоем
работы с контекстом пользователя:

1. помнить договорённости, задачи, контакты и источники;
2. находить и проверять нужную информацию;
3. превращать поток информации в краткие дайджесты и решения;
4. помогать планировать действия, но не выполнять рискованные действия без
   разрешения пользователя;
5. подключать специализированные роли-агенты, когда это действительно нужно.

Ключевой принцип: LLM предлагает понимание, план и текст; детерминированные
сервисы владеют данными и изменяют их только через проверенные операции.

## 2. Режимы работы

### 2.1 Task mode

Текущий режим: задачи, сроки, делегации, reminders, Gmail candidates и
Calendar actions. Он остаётся самым надёжным и предсказуемым.

- просмотр данных может выполняться без подтверждения;
- создание или изменение задачи требует явного действия пользователя;
- внешние сообщения, письма и события Calendar требуют отдельного
  подтверждения;
- каждое изменение проходит через сервисный слой и аудит.

### 2.2 Research mode

Режим ответа на вопросы пользователя:

```text
вопрос → классификация → поиск по разрешённым источникам →
извлечение evidence → проверка → ответ с источниками
```

Источники первой очереди:

- web search и открытые страницы;
- Gmail, только если пользователь разрешил поиск по почте;
- задачи, контакты и история ассистента;
- в будущем — документы, файлы и корпоративные базы.

Ответ должен разделять факты, выводы и неизвестное. Если источников нет или
они противоречат друг другу, ассистент сообщает об этом, а не заполняет пробел
догадкой. Для внешних источников сохраняются URL, время получения и цитируемый
фрагмент.

### 2.3 Digest mode

Пользователь сможет создать подписку, например:

> Каждый понедельник в 08:00: дайджест по AI safety и рынку AI, только новые
> материалы, 7–10 пунктов, с первоисточниками.

Подписка хранит тему, расписание, язык, список разрешённых источников,
глубину поиска, формат и лимит. Дайджест строится как отдельный job:

1. собрать материалы за окно времени;
2. убрать дубли и уже использованные статьи;
3. сгруппировать материалы по темам;
4. проверить ссылки и даты;
5. написать краткое резюме с citations;
6. отправить пользователю и сохранить результат.

Кроме scheduled digests нужны on-demand команды: «сделай дайджест за неделю»,
«только новости от официальных источников», «расширь пункт 3».

### 2.4 Orchestration mode

Сложные запросы разбиваются на план и отдельные роли:

- `researcher` — ищет материалы;
- `extractor` — извлекает факты и числа;
- `summarizer` — сводит результаты;
- `verifier` — проверяет claims и citations;
- `planner` — превращает выводы в варианты действий.

В первой версии это будут внутренние ограниченные роли поверх общего LLM
provider, а не свободно создающие друг друга автономные процессы. Вызов
субагентов выполняется только после разрешения пользователя и с показом:

- цели и плана;
- источников и доступов;
- ожидаемого времени;
- лимита запросов/tokens;
- действий, которые могут изменить данные или отправить наружу.

Субагент не получает весь контекст пользователя автоматически. Он получает
минимальный context packet, список разрешённых tools и deadline.

## 3. Разрешения и границы автономности

Нужна единая модель permission/approval, а не отдельные исключения в каждом
интеграционном модуле.

### Без подтверждения

- поиск в заранее разрешённых публичных источниках;
- чтение собственных задач и календаря;
- локальная классификация и суммаризация уже полученных данных;
- подготовка черновика или плана;
- отправка запланированного внутреннего дайджеста.

### С подтверждением

- создание, изменение или завершение задачи по результату research;
- создание или изменение Calendar event;
- отправка email, Telegram-сообщения или сообщения внешнему контакту;
- поиск по чувствительным источникам, если для них не задано постоянное
  разрешение;
- запуск субагентов с доступом к новым источникам;
- действия, расходующие заметный бюджет или выполняющиеся долго.

Каждое approval имеет TTL, scope, инициатора, план и idempotency key. Отказ,
истечение срока и выполнение решения также записываются в audit log.

## 4. Архитектура расширения

### 4.1 LLM Gateway и model router

Вместо единственной переменной `LLM_MODEL` нужен маршрутизатор:

- `LLM_MODEL_FAST` — дешёвая модель по умолчанию;
- `LLM_MODEL_REASONING` — более сильная модель для сложного planning/research;
- `LLM_MODEL_VERIFIER` — модель или отдельная проверка для claims/citations;
- `LLM_MAX_COST_PER_RUN` и `LLM_MAX_TOKENS_PER_RUN` — защитные лимиты.

Дешёвая модель подходит для:

- intent classification;
- извлечения task fields;
- простых ответов по локальным данным;
- форматирования и сжатия дайджестов;
- маршрутизации и подготовки tool calls.

Эскалация на более сильную модель происходит только при неоднозначности,
нескольких источниках, конфликте фактов, сложном плане или явном запросе
пользователя. Результат каждого запуска хранит model, latency, token usage,
стоимость, retry count и причину эскалации.

Router должен быть provider-neutral: конкретные модели задаются через
OpenClaw/OpenAI-compatible endpoint и конфигурацию окружения, без привязки
доменного кода к одному vendor.

### 4.2 Research layer

Нужен отдельный слой, не смешанный с `TaskService`:

- `ResearchRequest` — вопрос, scope и permission;
- `ResearchJob` — состояние выполнения и retry;
- `SourceDocument` — нормализованный источник;
- `EvidenceChunk` — цитируемый фрагмент с hash, URL и timestamp;
- `ResearchAnswer` — ответ, claims и ссылки на evidence.

Первый web connector должен возвращать нормализованные результаты, а не
передавать необработанный HTML напрямую в prompt. Private data из Gmail и
внутренних задач нельзя отправлять во внешний источник без явного разрешения.

### 4.3 Digest layer

Основные сущности:

- `DigestSubscription`;
- `DigestRun`;
- `DigestItem`;
- `DigestDelivery`;
- `DigestFeedback`.

Digest layer переиспользует дедупликацию и delivery state, уже применяемые в
daily reviews и reminders, но добавляет content fingerprint, source freshness
и повторное раскрытие конкретного пункта.

### 4.4 Job runtime

Текущий worker с несколькими бесконечными loops нужно постепенно дополнить
durable job execution:

- PostgreSQL-backed job table на первом этапе;
- `queued/running/succeeded/retry/dead_letter/cancelled`;
- lease/heartbeat для обнаружения зависшего worker;
- exponential backoff с jitter;
- idempotency key для каждого внешнего эффекта;
- отдельная ручная процедура replay из dead-letter;
- graceful shutdown: новые jobs не берутся, текущие завершаются или безопасно
  возвращаются в очередь.

Redis/Celery не нужны в первом шаге, пока одной PostgreSQL queue достаточно.
Их можно рассмотреть после появления нескольких worker replicas или высокой
нагрузки.

## 5. Надёжность и production safety

До увеличения автономности закрываем эксплуатационные риски:

1. offsite encrypted backups и регулярный restore drill;
2. alerting для backup, worker, Telegram polling, Gmail polling и disk usage;
3. metrics по latency, errors, retries, queue depth и LLM usage;
4. non-root deployment user и минимальные права файлов;
5. ротация Telegram, OpenClaw, database и OAuth secrets;
6. graceful shutdown и проверка полного reboot VPS;
7. отдельные health/readiness checks для DB, worker и integration loops.

Health endpoint должен показывать не только «процесс жив», но и деградацию:
последний успешный Telegram poll, последний Gmail poll, возраст очереди,
последний backup и доступное место на диске.

## 6. Продуктовый roadmap

### Phase 11 — Production hardening

- offsite backups;
- backup/worker/Telegram/disk alerting;
- metrics и расширенные health checks;
- non-root deployment;
- secret rotation;
- restore drill и полный reboot test.

### Phase 12 — Reliable job runtime

- durable jobs и leases;
- retry/backoff/dead-letter;
- worker watchdog;
- graceful shutdown;
- вынесение Gmail, reminders, digests и research в jobs;
- controlled replay и operator commands.

### Phase 13 — Research MVP

- вопрос в Telegram;
- поиск по разрешённым web sources;
- ответ с citations и датами;
- поиск по собственным задачам и Gmail с явным scope;
- дешёвый model router;
- audit и cost limits;
- без автоматических внешних действий.

### Phase 14 — Digest MVP

- subscriptions и расписания;
- allowlist источников;
- дедупликация материалов;
- дайджест за период и on-demand расширение;
- сохранение результата и feedback;
- retry/dead-letter доставки.

### Phase 15 — Controlled subagents

- внутренние роли researcher/extractor/verifier/planner;
- approval card в Telegram;
- ограниченные tools и context packets;
- budget/deadline/parallelism limits;
- трассировка parent run → child runs → tool calls;
- запрет внешних side effects без отдельного approval.

### Phase 16 — Product depth

- recurring tasks;
- полноценные contacts и entity resolution;
- улучшенные daily/evening reviews;
- двусторонний Calendar sync и event reminders;
- история изменений и полнотекстовый поиск;
- Gmail task suggestions с фильтрами и дедупликацией.

### Phase 17 — Multi-user platform

- web dashboard;
- users, workspaces, roles и permissions;
- browser authentication и session management;
- dashboard для задач, research runs, digests, logs и integrations;
- WhatsApp/voice channels после стабилизации permission model.

## 7. Первый пользовательский MVP

Пользователь должен получить такой сценарий:

```text
«Что нового за неделю по теме X?»
        ↓
«Найти только официальные источники и публикации после даты Y?»
        ↓
research job с дешёвой моделью и лимитом
        ↓
ответ: 5–7 тезисов, ссылки, даты, уровень уверенности
        ↓
«Сделай из этого дайджест по понедельникам»
        ↓
approval → DigestSubscription → scheduled delivery
```

Сложный сценарий:

```text
«Сравни варианты и подготовь план»
        ↓
показать план и запросить разрешение на researcher + verifier
        ↓
субагенты работают в sandbox и возвращают evidence
        ↓
ассистент показывает вывод и отдельно предлагает действия
        ↓
любое изменение задачи/календаря/внешнее сообщение — отдельное подтверждение
```

## 8. Что не делать сразу

- не давать LLM прямой доступ к базе;
- не разрешать свободное самозарождение субагентов;
- не отправлять внешние сообщения по одной только рекомендации модели;
- не начинать с dashboard и multi-user до стабилизации job/permission model;
- не подключать дорогую reasoning model ко всем сообщениям;
- не смешивать web search, Gmail search и внутренний task search без явного
  отображения scope пользователю.

## 9. Предлагаемое ближайшее решение

Следующим рабочим шагом предлагается не сразу писать весь research platform,
а выполнить два коротких этапа:

1. Phase 11: закрыть production risks и добавить базовые metrics/health;
2. Phase 12: ввести durable jobs и model router;
3. затем сделать вертикальный Research MVP: один Telegram-вопрос, один
   разрешённый web connector, citations, cost limit и read-only ответ.

После этого будет понятно, какие источники, лимиты и субагенты реально нужны,
а не только выглядят полезными на уровне списка возможностей.
